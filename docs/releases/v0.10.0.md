## What is available

This milestone publishes the substantially expanded [CSP consumer-security specification](https://github.com/sankarshanmukhopadhyay/ERC-8004-CSP/blob/main/spec/erc-8004-csp.md). It defines **105 traceable consumer requirements**, preserves the cumulative L0–L4 level names, and identifies the security controls required to interpret ERC-8004 identity, reputation and validation registry records without overstating their meaning.

The accompanying package includes a source-pinned [requirements catalogue](https://github.com/sankarshanmukhopadhyay/ERC-8004-CSP/blob/main/conformance/requirements.json), **47 descriptive conformance scenarios**, **26 bounded synthetic normalized-evidence decision vectors**, Keccak/identifier/strict-JSON security regressions, the experimental OPA/Rego display-admission evaluator, deployment and owner-epoch safeguards, and a [finding-by-finding red-team disposition](https://github.com/sankarshanmukhopadhyay/ERC-8004-CSP/blob/main/docs/red-team-resolution-2026-11.md).

The GitHub Pages site exposes the specification and associated repository source through a derived catalogue: [ERC-8004-CSP documentation](https://sankarshanmukhopadhyay.github.io/ERC-8004-CSP/). The **tagged source** is the immutable publication reference.

## BREAKING CHANGE: evidence semantics

**Embedded `data:` URI content is bound to the observed on-chain URI; it is not automatically independently digest-authenticated external content.** A consumer that treated embedded bytes as an independently verified content anchor under earlier CSP wording must reclassify or reevaluate the corresponding display or assurance claim.

Other material interpretive boundaries:

- Preserve the upstream namespace-qualified `agentRegistry` and numeric `agentId`; do not silently collapse a full registry namespace into the Rego adapter's address-only field.
- Verify ERC-8004 request, feedback and validation commitments with **Ethereum Keccak-256**, not NIST SHA3-256 and not an unrelated local `sha256:` evidence identifier.
- Distinguish agent-lifetime evidence from the current owner's epoch, recognize a registry deployment and its ABI/code identity, and re-evaluate affected evidence after relevant ownership, implementation, URI or wallet changes.
- Do not present selected-client reputation, validator responses, endpoint domain control, or evidence freshness as universal safety, independent assurance or authority to act.

**Migration:** continue using the v0.9.1 configuration schema if you need the legacy contract, but do not promote v0.9.1 claims to the strengthened v0.10.0 interpretation without inspecting the affected evidence. New candidate policy controls require a deliberate adopter-specific migration, including corresponding runtime enforcement and test evidence. Retain historical claims under their original evaluation version.

## Validation and provenance

Source-to-requirement generation, pinned ERC-8004 heading references, JSON Schema examples, 47 descriptive scenario identifiers, secure-parser and Keccak negative vectors, 26 normalized-evidence fixtures, and real OPA policy execution are checked by repository GitHub Actions. The release automation additionally requires the **Pages/traceability** and **Rego/security** workflows to pass for the exact release-head commit. The published GitHub Release records that commit and the workflow-run links.

**Do not interpret these results as an executed end-to-end CSP conformance test suite.** A descriptive scenario is not an actual consumer-path PASS. A normalized fixture contains author-supplied assertions and does not authenticate an upstream chain, fetch remote data, validate a TEE, or enforce agent authority.

## Important limitations and next evidence

No production-grade chain/ABI resolver, verified source finality, bounded end-to-end network fetching, independent reviewer/validator qualification, real AI tool-boundary injection isolation, enforceable external economic guarantee, or delegated-action authorization is established by this release. ERC-8004 itself remains a Draft and may change.

These independent implementation and adoption questions remain recorded in [Issue #10](https://github.com/sankarshanmukhopadhyay/ERC-8004-CSP/issues/10). The original upstream-alignment and bounded Rego scope was completed under [Issue #4](https://github.com/sankarshanmukhopadhyay/ERC-8004-CSP/issues/4).

**Authority statement:** CSP is a consumer-governed profile. This release does not claim Ethereum/ERC endorsement, independent assessment, conformance certification or production interoperability.
